# 쿠버네티스 워크로드

# 1. Pods

- 컨테이너의 공동 배포된 그룹이며 쿠버네티스의 기본 빌딩 블록을 대표
- 쿠버네티스는 컨테이너를 개별적으로 배포하지 않고 컨테이너의 파드를 항상 배포하고 운영
- 일반적으로 파드는 단일 컨테이너만 포함하지만 다수의 컨테이너를 포함 할 수 있음
- 파드는 다수의 노드에 생성되지 않고 단일 노드에서만 실행
- 여러 프로세스를 실행하기 위해서는 컨테이너 당 단일 프로세스가 적합
- 다수의 프로세스를 제어하려면? → 다수의 컨테이너를 다룰 수 있는 그룹이 필요!

## 동일 Pod의 컨테이너 사이 부분 격리

- 파드의 모든 컨테이너는 동일한 네트워크 및 UTS 네임스페이스에서 실행
- 같은 호스트 이름 및 네트워크 인터페이스를 공유 (포트 충돌 가능성 있음)
- 파드의 모든 컨테이너는 동일한 IPC 네임스페이스 아래에서 실행되며 IPC를 통해 통신 가능
    - 최신 쿠버네티스 및 도커 버전에서는 동일한 PID 네임스페이스를 공유할 수 있지만 이 기능은 기본적으로 활성화돼 있지 않다

![Untitled](%EC%BF%A0%EB%B2%84%EB%84%A4%ED%8B%B0%EC%8A%A4%20%EC%9B%8C%ED%81%AC%EB%A1%9C%EB%93%9C/Untitled.png)

- 실행 중인 파드는 클러스터의 가상 네트워크에 포함돼 있음
- 외부에서 액세스하려면 서비스 객체를 통해 IP를 노출하는 것이 필요
- LoadBalancer라는 서비스를 작성하면 외부 로드 밸런서가 생성
- 로드 밸런서의 공인 IP를 통해 파드에 연결 가능 (하지만 로컬 쿠버네티스에서는 동작하지 않으며 externalDNS가 필요함, 이 기능은 GKE, EKS 같은 클라우드에서 사용 가능(구글, AWS 계정 필요))

# 2. Probe

## 2.1 Liveness Probe

- 컨테이너 살았는지 판단하고 다시 시작하는 기능
- 컨테이너의 상태를 스스로 판단하여 교착 상태에 빠진 컨테이너를 재시작
- 버그가 생겨도 높은 가용성을 보임
    
    exec-liveness.yaml
    

```yaml
apiVersion: v1
kind: Pod
metadata:
  labels:
    test: liveness
  name: liveness-exec
spec:
  containers:
  - name: liveness
    image: k8s.gcr.io/busybox
    args:
    - /bin/sh
    - -c
    - touch /tmp/healthy; sleep 30; rm -rf /tmp/healthy; sleep 600
#커맨드 성공시 0, 실패하면 그 외 값 출력 (컨테이너 재시작)
    livenessProbe:
      exec:
        command:
        - cat 
        - /tmp/healthy
      initialDelaySeconds: 5
      periodSeconds: 5
```

http-liveness.yaml

```yaml
apiVersion: v1
kind: Pod
metadata:
  labels:
    test: liveness
  name: liveness-http
spec:
  containers:
  - name: liveness
    image: k8s.gcr.io/liveness
    args:
    - /server
# 서버응답코드가 200이상 400미만이면 정상, 그외는 컨테이너 재시작
    livenessProbe:
      httpGet:
        path: /healthz
        port: 8080
        httpHeaders:
        - name: Custom-Header
          value: Awesome
      initialDelaySeconds: 3
      periodSeconds: 3
```

## 2.2 Readiness Probe

- 파드가 준비된 상태에 있는지 확인하고 정상 서비스를 시작하는 기능
- 파드가 적절하게 준비되지 않은 경우 로드밸런싱을 하지 않음
    
    tcp-liveness-readiness.yaml
    

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: goproxy
  labels:
    app: goproxy
spec:
  containers:
  - name: goproxy
    image: k8s.gcr.io/goproxy:0.1
    ports:
    - containerPort: 8080
#최초 5초 후 8080포트를 검사하고 10초 간격 검사진행, 서비스 가능여부 판단
    readinessProbe:
      tcpSocket:
        port: 8080
      initialDelaySeconds: 5
      periodSeconds: 10
# 최초 15초 후 8080포트 검사, 검사주기는 20초
    livenessProbe:
      tcpSocket:
        port: 8080
      initialDelaySeconds: 15
      periodSeconds: 20
```

## 2.3 Startup Probe

- 애플리케이션의 시작 시기 확인하여 가용성을 높이는 기능
- Liveness 와 Readiness 의 기능을 비활성화

```yaml
ports:
- name: liveness-port
	containerPort: 8080
	hostPort: 8080

livenessProbe:
	httpGet:
		path: /healthz
		port: liveness-port
	failureThredhold: 1
	periodSeconds: 10
# 시작할때까지 검사를 수행 (해당 URI로 http요청하여 검사)
startupProbe:
	httpGet:
		path: /healthz
		port: liveness-port
	failureThreshold: 30
	periodSeconds: 10
```

# 3. Label/Selector

## 3.1 Label

- 리소스에 첨부하는 임의의 키/값 쌍(예 app: test)
- 레이블 셀렉터를 사용하면 각종 리소스를 필터링하여 선택할 수 있음
- 리소스는 한 개 이상의 레이블을 가질 수 있음
- 리소스를 만드는 시점에 레이블을 첨부
- 기존 리소스에도 레이블의 값을 수정 및 추가 가능
- 모든 사람이 쉽게 이해할 수 있는 체계적인 시스템을 구축 가능
    - app: 애플리케이션 구성요소, 마이크로서비스 유형 지정
    - rel: 애플리케이션의 버전 지정

# 4. ReplicaSet

- 파드가 항상 실행되도록 유지하는 쿠버네티스 리소스
- 노드가 클러스터에서 사라지는 경우 해당 파드를 감지하고 대체 파드 생성
- 실행 중인 파드의 목록을 지속적으로 모니터링으로 하고 '유형'의 실제 파드 수가 원하는 수와 항상 일치하는지 확인

## 4.1 ReplicaSet의 요소

- 레이블 셀렉터 : 레플리케이션 컨트롤러가 관리하는 파드 범위를 결정
- 복제본 수 : 실행해야하는 파드의 수를 결정
- 파드 템플릿 : 새로운 파드의 모양을 설명

http-go-rs.yaml

```yaml
apiVersion: apps/v1
kind: ReplicaSet
metadata:
	name: frontend
	labels:
		app: guestbook
		tier: frontend
spec:
	replicas: 3 #복제본 수
	selector:
		matchLabels:
			tier: frontend #관리 파드의 범위를 결정
	template: #새로운 파드의 모양을 설명
		metadata: 
			labels:
				tier: frontend
		spec:
			containers:
			- name: php-redis
			  image: gcr.io/google_samples/gb-frontend:v3
```

레플리케이션 컨트롤러는 레플리카셋의 구버전으로 완전 대체됨 (호환성을 위한 기능 보존)

## 5.2 Deployment Update 전략

- Rolling Update(기본값)
    - 오래된 파드를 하나씩 제거하는 동시에 새로운 파드 추가
    - 요청을 처리할 수 있는 양은 그대로 유지
    - 반드시 이전 버전과 새 버전을 동시에 처리 가능하도록 설계한 경우에만 사용해야 함
- Recreate
    - 새 파드를 만들기 전에 이전 파드를 모두 삭제
    - 여러 버전을 동시에 실행 불가능
    - 잠깐의 다운 타임 존재
- 업데이트 과정을 보기 위해 업데이트 속도 조절

```bash
$ kubectl patch deployment http-go -p '{"spec": {"minReadySeconds": 10}}'
deployment.extensions/http-go patche
```

### Deployment 업데이트 실행

```bash
$ kubectl set image deployment http-go http-go=gasbugs/http-go:v2
deployment.extensions/http-go image updated

$ kubectl rollout history deployment http-go # 업데이트 이력 확인
deployment.extensions/http-go
```

### Rollback 실행

```bash
$ kubectl set image deployment http-go http-go=gasbugs/http-go:v3
deployment.extensions/http-go image updated
**$ kubectl rollout undo deployment http-go**
deployment.extensions/http-go
$ kubectl exec http-go-7dbcf5877-d6n6p curl 127.0.0.1:8080
Welcome! http-go:v2
$ kubectl rollout undo deployment http-go --to-revision=1
deployment.extensions/http-go
```

# 6. 네임스페이스

- 리소스를 각각의 분리된 영역으로 나누기 좋은 방법
- 여러 네임스페이스를 사용하면 복잡한 쿠버네티스 시스템을 더 작은 그룹으로 분할
- 멀티 테넌트(Multi-tenant) 환경을 분리하여 리소스를 생산, 개발, QA 환경 등으로 사용
- 리소스 이름은 네임스페이스 내에서만 고유 명칭 사용
- kubectl get 을 옵션없이 사용하면 default 네임스페이스에 질의
- 다른 사용자와 분리된 환경으로 타인의 접근을 제한
- 네임스페이스 별로 리소스 접근 허용과 리소스 양도 제어 가능
- --namespace나 -n을 사용하여 네임스페이스 별로 확인이 가능
